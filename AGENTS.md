# AGENTS.md

## Project overview

SHIFT64 Phone Validation for WooCommerce is a WordPress/WooCommerce plugin that validates and formats billing and shipping phone numbers at checkout, using Google's libphonenumber (`giggsey/libphonenumber-for-php-lite` v9). It parses a number against the address country, rejects numbers that are not real for that country, and optionally rewrites valid numbers into one consistent output format (E.164, international, or national) before they are stored on the order. It supports both the classic shortcode checkout and the block checkout (Store API), and ships English and Polish translations. It has no self-updater and makes no outgoing HTTP requests: it is distributed through the WordPress.org plugin directory, which serves its updates, and every GitHub release carries the same package as `shift64-phone-validation.zip` for manual installs (D05 in `.ai/specs/product-brief.md`).

The plugin needs PHP 8.3+, WordPress 7.1+ and WooCommerce 7.2+ (`BACKWARD_COMPATIBILITY.md` §5; the WordPress minimum is also `minimum_wp_version` in `.phpcs.xml.dist`, kept equal to `SHIFT64_PHONE_VALIDATION_MIN_WP`), is PSR-4 autoloaded under `Shift64\SmartPhoneValidation` from `src/`, and has no JS build step — the two files in `assets/js/` are shipped as-is.

## Task routing

| When the task involves… | Read first | Key rules |
|---|---|---|
| Parsing, validating, or normalizing a number | `src/Validation/PhoneValidator.php`, `src/Validation/Normalizer.php`, `src/Validation/ValidationResult.php` | The validator returns a `ValidationResult` value object, never a bare bool or an exception — callers branch on it. `Normalizer` runs first and is where input cleanup lives (non-breaking spaces, dashes, dots, slashes, parentheses, leading `00` → `+`); do not scatter cleanup into callers. libphonenumber is reached only through these classes. |
| Output formatting | `src/Formatter/PhoneFormatter.php` | Formats are the `FORMAT_*` constants; a new format means a new constant plus a settings option, not a raw string passed through. |
| Classic (shortcode) checkout | `src/Checkout/BillingPhoneValidator.php`, `src/Checkout/ShippingPhoneValidator.php`, `src/Checkout/Hooks.php` | Shipping phone is optional: validate only when non-empty. Hook signatures come from WooCommerce, so unused parameters are expected and are excluded from the unused-parameter sniff in `.phpcs.xml.dist`. |
| Block checkout / Store API | `src/Checkout/BlockCheckoutValidator.php` | Errors are returned through the Store API error shape, not echoed. Language for messages follows Polylang / WPML (`wpml_current_language`); do not assume the site locale. Switch with `switch_to_locale()` / `restore_previous_locale()` only: never `unload_textdomain()` or `load_plugin_textdomain()` inside a request, which left the messages in English on WordPress 6.7+ (#32). The domain's `languages/` folder is registered once, by the main plugin file. |
| Error messages and i18n | `src/Checkout/ErrorMessages.php`, `languages/` | Every user-facing string is translated with the `shift64-phone-validation` text domain — PHPCS enforces the domain. After changing strings run `composer makepot` (it pins `--slug=shift64-phone-validation`), then update the `.po` files with `wp i18n update-po` (`composer makepo`) and compile the `.mo` files with `wp i18n make-mo` (`composer makemo`); WP-CLI ships in the dev dependencies as `vendor/bin/wp`. Messages are filterable via `shift64_phone_validation_error_message`. The only `load_plugin_textdomain()` call is in the main plugin file, on `plugins_loaded` priority 5: WordPress 7.1 registers `languages/` from the `Domain Path` header itself only for plugins activated per site, so a network-activated install needs it, and since 6.7 it only registers the folder (no file is loaded; a language pack from translate.wordpress.org still wins). Plugin Check reports it as a non-failing warning (`load_plugin_textdomainFound`), accepted (D07). |
| Checkout JS / field highlighting | `assets/js/checkout-validation.js`, `assets/js/block-checkout-validation.js`, `src/Checkout/Assets.php` | No build step — edit the shipped files directly. Enqueueing is opt-out through `shift64_phone_validation_enqueue_assets` for themes with their own error UX; keep that escape hatch working. |
| Settings screen or plugin options | `src/Admin/Settings.php`, `src/Admin/PluginScreen.php`, `uninstall.php` | Options are prefixed `shift64_phone_validation_*`. A new option must also be deleted in `uninstall.php`, or it leaks after uninstall. `PluginScreen` adds the Settings link on the Plugins screen and the one-time redirect after activation; the redirect replaces only `plugins.php?activate=true` and keeps its exceptions (bulk / network activation, WP-CLI, AJAX, REST, another user) — WordPress.org guideline 11 forbids hijacking the admin. |
| Distribution: WordPress.org directory, SVN deploy, release ZIP | `.distignore`, `scripts/build-package.sh`, `.github/workflows/release.yml`, `.github/workflows/wporg-deploy.yml`, `.github/workflows/wporg-assets.yml`, `.wordpress-org/` | No update checker and no other remote calls: serving updates from anywhere but WordPress.org breaks Detailed Plugin Guideline 8, which is why the GitHub self-updater was removed (D05). The built package must pass Plugin Check with 0 errors; the `package` job in `code-quality.yml` proves it on every PR. One package is built per release and goes both to the GitHub release and to WordPress.org SVN; `release.yml` skips the SVN deploy until the `SVN_USERNAME` / `SVN_PASSWORD` secrets exist. `wporg-deploy.yml` (manual) rebuilds a tag and re-attaches `shift64-phone-validation.zip` to its GitHub release (`upload-zip`) and/or deploys it to SVN (`svn`); only the SVN deploy needs the SVN secrets, and it refuses a tag that is not the latest GitHub release unless `allow-older` is set (an older tag would overwrite SVN trunk and move `Stable tag` back). `wporg-assets.yml` pushes `readme.txt` and `.wordpress-org/` only once `tags/<Stable tag>` exists in SVN. Anything at the repo root that is not runtime code goes in `.distignore`. Directory listing assets (icon, banners, screenshots) live in `.wordpress-org/` and never ship in the package. |
| Plugin bootstrap, constants, WooCommerce compatibility | `shift64-phone-validation.php` | The version lives in three places kept in sync by `scripts/update-version.sh` (plugin header, `SHIFT64_PHONE_VALIDATION_VERSION`, `readme.txt` `Stable tag`), which also prepends the new release from `CHANGELOG.md` to the `readme.txt` changelog via `scripts/sync-readme-changelog.php` (it never rewrites existing entries and keeps the 10 most recent versions) — never edit the version or add release entries to that changelog by hand; semantic-release runs the script. ## Validation gate

Run in this order; any non-zero exit blocks the PR:

- `composer install --prefer-dist --no-interaction`
- `composer phpcs`
- `composer phpstan`
- `composer test`

`vendor/` is git-ignored, so the install step is genuinely required in a fresh clone or worktree. PHPCS runs `WordPress-Extra` plus `PHPCompatibilityWP` at `testVersion 8.3-`, with `minimum_wp_version` 7.1 for the WordPress sniffs (keep it equal to `SHIFT64_PHONE_VALIDATION_MIN_WP`); `tests/`, `scripts/` and `vendor/` (plus `node_modules/`, `dist/` and `assets/build/`) are excluded from the scan. PHPStan (`phpstan.neon.dist`) runs at level 6 with no baseline on `src/`, the main plugin file and `uninstall.php`, against PHP 8.3, with the WordPress extension and the WooCommerce stubs; `tests/` is not analysed. It also gates every release: `release.yml` runs it in a `static-analysis` job that the `release` job needs. Indentation is tabs, per the WordPress standard — match the file you are editing.
